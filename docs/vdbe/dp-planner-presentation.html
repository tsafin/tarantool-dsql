01 / задача

Один запрос — много способов выполнить

SQL
SELECT ... FROM A JOIN B ON ... JOIN C ON ... WHERE A.x = 7;

Нужно выбрать порядок таблиц и способ доступа к каждой: сканирование или индекс.

Физическое исполнение сегодня

Вложенные циклы

for outer in A: for middle in lookup(B, outer): for inner in lookup(C, middle): emit row

JOIN-планировщик пока не выбирает hash или merge join.

Порядок циклов влияет на число повторных обращений к внутренней таблице.
02 / что такое DP

DP = dynamic programming

Строим снизу вверх: короткий частичный план переиспользуется как основа длинного. Не начинаем с полного JOIN и не рекурсивно разбиваем его сверху вниз.

«Мемо» здесь — два ограниченных массива WherePath, а не полная таблица всех подмножеств.
03 / почему порядок важен

5 обращений или 1 000?

У A — 1 000 строк, у B — 5. Допустим, для внутренней таблицы доступен индекс по ключу JOIN.

A снаружи

A → lookup(B)

1 000
примерно столько индексных поисков в B
B снаружи

B → lookup(A)

5
примерно столько индексных поисков в A

Это учебный пример числа probes, не обещание 200× ускорения: цена каждого поиска, результат JOIN и другие предикаты тоже важны.

04 / состояние DP

Путь — это больше, чем цена

Два пути по одним таблицам могут оба быть полезны: один дешевле сейчас, другой выдаёт меньше строк или сохраняет нужный порядок.

05 / beam width

«Глобальный лимит» — один на весь уровень

Упрощённый пример: beam = 3. После расширения до двух таблиц сохраняются не три пути на каждое подмножество, а не более трёх путей суммарно.

В коде отбор происходит по мере появления кандидатов. Реальный лимит по умолчанию: 1 / 5 / 10 для 1 / 2 / ≥3 таблиц.

06 / два фильтра

Доминирование ≠ beam-отсечение

1. Доминирование

Сравним только сопоставимые пути

Одинаковые набор таблиц, удовлетворённый ORDER BY и направление сканирования. Если один путь не хуже по rCost, rUnsorted и nRow, худший удаляется.

2. Полный beam

Места кончились

Даже недоминируемый путь может быть отброшен. Новый кандидат должен вытеснить сохранённый; предпочтение — худшему пути из группы с несколькими вариантами.

Сгенерировано
много
После отбора
≤ beam

Следствие: DP находит минимальную оценённую стоимость среди сохранённых полных путей, не обязательно среди всех возможных.

07 / область поиска

Какие JOIN вообще участвуют?

Поддерживаются

INNER, запятая, CROSS, LEFT OUTER; NATURAL и USING разрешаются до планирования. CROSS и LEFT накладывают зависимости на допустимый порядок.

До 64 элементов FROM за один вызов WHERE-планировщика.

Не являются вариантами DP

RIGHT/FULL отклоняются. Явный SEMI/ANTI JOIN, hash join и merge join не входят в физическое пространство текущего DP.

EXISTS/IN имеют сходную семантику через другие механизмы, не отдельные JOIN-операторы здесь.

08 / откуда берётся цена

Статистика уже работает — но не вся

Уже в живом планировщике

Размер таблицы, среднее число строк на префикс индекса, MCV для ограниченного набора литеральных равенств.

Ещё не подключено

Гистограммная селективность диапазонов, общая корреляция JOIN и multivariate-оценка промежуточных результатов.

09 / memtx и Vinyl

Два движка — одна формула стоимости

memtx

Данные в памяти

Статистика собирается по memtx-таблицам. Текущая оценка доступа использует общие эвристики scan / seek / fetch.

Vinyl

LSM-хранилище

Статистика собирается по Vinyl-таблицам, но та же формула не оценивает отдельно run/level, кэш, bloom-фильтры и secondary→primary amplification.

Разные оценки числа строк ≠ разные cost functions движков

Новая M3-модель тоже пока приближённая: startup/total есть в структуре, но живой адаптер в основном выводит цену из числа строк.

11 / ближайшие действия

Как решить, нужен ли другой DP

Дорожки 1–3 можно вести параллельно. Решение о production-алгоритме — только после сравнения на одинаковых данных и статистике, отдельно для обоих движков.

12 / итог

Что важно запомнить

DP

План строится снизу вверх из сохранённых частичных путей.

10

Максимум путей на уровень для ≥3 таблиц по умолчанию — глобально, не на подмножество.

≠

Лучшая оценённая стоимость не равна гарантированно лучшему реальному времени.
