## The Pattern to Watch

This audit was triggered by discovering OP_Clear bug (now fixed):

```c
// DANGEROUS - Before fix
if (pOp->p2 > 0) {
    // Handle TRUNCATE case
    box_truncate(space_id);
}
// ❌ MISSING else block = Silent failure when P2==0 (DELETE case)

// SAFE - After fix (commit 2fb0c16c34)
if (pOp->p2 > 0) {
    // Handle TRUNCATE case
    box_truncate(space_id);
} else {
    // Handle DELETE case
    tarantoolsqlClearTable(space, &tuple_count);
    if (p5 & OPFLAG_NCHANGE)
        p->nChange += tuple_count;
}
```

**Result**: DELETE FROM now works. Lesson: Must implement ALL branches in P2-driven conditionals.

## What We Found

### Critical (1 handler) ⚠️ URGENT

**OP_Once** (lines 47-61 in vdbe_ops_inline_medium_4.c)
- Current logic: `if (flag_is_set) jump; else continue`
- Problem: Should be `if (flag_is_clear) {set_flag; jump}; else {skip}`
- Impact: Trigger/initialization code runs repeatedly instead of once
- **Action**: Verify against `/src/box/sql/vdbe.c` inline implementation
- **Command**: `grep -A 40 "EXECUTE(OP_Once" src/box/sql/vdbe.c`

### Medium (2 handlers) ⚠️ VERIFY

**OP_Last** (lines 37-66 in vdbe_ops_cursor_nav.c)
- Issue: `assert(pOp->p2 == 0)` in else branch - too strict?
- May reject valid bytecode if compiler generates OP_Last with P2>0 and P3!=0
- **Action**: Check SQL compiler bytecode generation for OP_Last

**OP_MustBeInt** (lines 15-27 in vdbe_ops_type.c)
- Issue: Error handling paths need verification
- Pattern: `if (conversion_fails) { if (p2!=0) jump; else error; }`
- **Action**: Compare error paths with inline dispatcher

### Low (1 handler) ❌ INCOMPLETE BUT UNUSED

**OP_GetItem** (lines 266-293 in vdbe_ops_inline_medium_7.c)
- Status: Non-functional stub with TODO comment
- Impact: NONE - Not generated by SQL compiler

### Safe (21 handlers) ✅ VERIFIED

All follow one of three safe patterns:

**Pattern 1: Return Code Branching (12 handlers)**
- Handlers return 0/1/-1 to signal action
- P2 is only jump target (not condition value)
- Examples: Next, Prev, Rewind, Last, sorter operations
- Status: Safe - clear semantics

**Pattern 2: Flag-Based Branching (8 handlers)**
- Check P5 flags, not P2 values
- Both code paths fully implemented
- Examples: Eq, Ne, Lt, Le, Gt, Ge, Compare
- Status: Safe - symmetric implementation

**Pattern 3: Data Flow (3 handlers)**
- P2 is source/destination register or immediate value
- No conditional branching
- Examples: AddImm, Sequence, Fetch
- Status: Safe - no control flow issues

## The OP_Clear Reference Pattern

Learn from this fix (commit 2fb0c16c34):

**Symptoms**: DELETE FROM not working, rows not deleted
**Root Cause**: P2==0 branch missing in OP_Clear handler
**Pattern**: Parameter-driven branching with missing else block

**How to avoid**:
1. When P2 controls operation mode, implement BOTH branches
2. Test both P2>0 and P2==0 cases
3. Look for: `if (pOp->p2 > 0)` without corresponding `else`
4. Silent failures are worse than errors - always implement both paths
